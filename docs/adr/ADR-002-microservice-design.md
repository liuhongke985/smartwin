# ADR-002: 微服务设计策略

## 状态
已接受 (Accepted)

## 日期
2026-01-20

## 背景与问题陈述

SmartWin 平台需要决定如何拆分微服务边界，以及选择合适的服务间通信方式。不当的微服务拆分会导致分布式单体（Distributed Monolith）问题。

## 决策驱动因素

1. **业务边界清晰**: 每个服务应有明确的业务职责
2. **独立部署**: 服务可以独立开发、测试、部署
3. **技术异构**: 支持不同服务使用不同技术栈
4. **数据自治**: 每个服务管理自己的数据
5. **团队对齐**: 服务粒度与团队结构对应

## 微服务拆分原则

### DDD 限界上下文

基于领域驱动设计(DDD)识别限界上下文：

```
SmartWin Platform
├── 数据治理上下文 (SmartData)
│   ├── 数据资产管理
│   ├── 数据质量管理
│   └── 数据血缘管理
├── AI协同上下文 (SmartChain)
│   ├── AI链引擎
│   ├── LLM集成
│   └── 工作流管理
└── 平台支撑上下文
    ├── 身份认证
    ├── 网关路由
    └── 监控告警
```

## 服务通信策略

### 同步通信 (HTTP/REST)
适用场景：
- 需要立即得到响应的操作
- 查询类请求
- 用户交互触发的操作

### 异步通信 (Message Queue)
适用场景：
- 事件通知
- 耗时操作（AI分析、数据质量检测）
- 多服务需要响应同一事件

**消息队列选型:** RabbitMQ (默认) + Kafka (大流量场景)

| 场景 | 使用RabbitMQ | 使用Kafka |
|------|------------|---------|
| 任务调度 | ✓ | |
| 数据流处理 | | ✓ |
| 事件通知 | ✓ | |
| 日志收集 | | ✓ |

## 数据管理策略

### 每个服务独立数据库 (Database per Service)
- SmartData 使用独立 MySQL 数据库
- SmartChain 使用独立 MySQL + Neo4j
- 禁止跨服务直接访问数据库

### 数据一致性
- 优先使用最终一致性
- 跨服务事务使用 Saga 模式
- 关键业务操作使用 Outbox 模式保证可靠性

## 服务网格考量

当前阶段不引入服务网格 (如 Istio)，原因：
- 增加架构复杂度
- 团队学习成本
- 项目规模尚不需要

未来在服务数量 > 20 时重新评估。

## 结果与影响

**正面影响:**
- 清晰的服务边界降低耦合
- 支持独立扩展高负载服务
- 障碍隔离，单服务故障不影响整体

**负险:**
- 分布式系统复杂性增加
- 网络延迟开销
- 分布式追踪需要额外投入
