## 1. 代码审查概述

### 1.1 审查目标

| 目标 | 说明 |
|------|------|
| 质量保障 | 早期发现缺陷，降低修复成本 |
| 知识共享 | 团队成员互相学习，统一编码风格 |
| 架构一致性 | 确保代码符合架构设计规范 |
| 安全保障 | 发现潜在安全漏洞 |

### 1.2 审查原则

| 原则 | 说明 |
|------|------|
| 强制审查 | 所有代码合入前必须经过审查 |
| 至少一人 | 每个MR至少1名审查人批准 |
| 关键路径两人 | 核心模块/公共模块需2名审查人 |
| 24小时响应 | 审查人应在24小时内响应 |
| 对事不对人 | 审查代码而非审查人 |

## 2. 审查流程

### 2.1 MR/MR流程

```
开发完成 → 自检 → 提交MR → CI检查 → 人工审查 → 修改 → 批准 → 合入
              │                      │         │
         自检清单            自动化检查   审查意见
```

### 2.2 MR要求

| 要求 | 说明 |
|------|------|
| MR标题 | 遵循Commit Message规范 |
| MR描述 | 说明变更内容、原因、影响范围 |
| 关联Issue | MR关联对应Issue/Task |
| 单元测试 | 新增/修改代码需附带单测 |
| CI通过 | 编译+测试+扫描全部通过 |
| 冲突解决 | MR无合并冲突 |

## 3. 审查检查清单

### 3.1 通用检查项

| 序号 | 检查项 | 说明 |
|:----:|--------|------|
| 1 | 命名规范 | 变量/方法/类命名符合规范 |
| 2 | 代码格式 | 缩进/空格/换行符合规范 |
| 3 | 注释完整 | 复杂逻辑有注释，公开API有JavaDoc |
| 4 | 无TODO | 临时代码/TODO需说明原因和时间 |
| 5 | 无硬编码 | 魔法数字/字符串提取为常量 |
| 6 | 无死代码 | 删除无用代码/注释掉的代码 |

### 3.2 Java专项检查

| 序号 | 检查项 | 说明 |
|:----:|--------|------|
| 1 | 分层正确 | Controller无业务逻辑，Service无数据库操作 |
| 2 | 事务管理 | @Transactional使用正确，无大事务 |
| 3 | 异常处理 | 使用统一异常体系，不吞异常 |
| 4 | 空指针防护 | Optional或显式null检查 |
| 5 | 集合安全 | 使用不可变集合或防御性拷贝 |
| 6 | 日志规范 | 日志级别正确，含上下文信息 |
| 7 | 线程安全 | 共享变量线程安全 |
| 8 | 资源释放 | IO/连接正确关闭(try-with-resources) |

### 3.3 安全检查项

| 序号 | 检查项 | 说明 |
|:----:|--------|------|
| 1 | SQL注入 | 使用参数化查询，禁止字符串拼接SQL |
| 2 | XSS防护 | 输出编码，禁止v-html |
| 3 | 敏感数据 | 密码/密钥不明文打印日志 |
| 4 | 权限校验 | API有权限注解或网关校验 |
| 5 | 输入校验 | 所有外部输入有校验 |
| 6 | 依赖安全 | 无已知漏洞的依赖 |

### 3.4 前端检查项

| 序号 | 检查项 | 说明 |
|:----:|--------|------|
| 1 | 响应式数据 | ref/reactive使用正确 |
| 2 | 内存泄漏 | 定时器/事件监听器正确销毁 |
| 3 | 组件通信 | Props/Emits定义类型 |
| 4 | API调用 | 统一使用封装的request |
| 5 | 国际化 | 文本使用i18n，无硬编码中文 |
| 6 | 无障碍 | 语义化HTML，aria标签 |

## 4. 审查级别

### 4.1 级别定义

| 级别 | 适用范围 | 审查人 | 批准数 |
|:----:|----------|--------|:------:|
| L1-标准 | 普通业务代码 | 任意开发 | 1 |
| L2-重要 | 公共模块/核心业务 | 开发Lead | 1 |
| L3-关键 | 架构变更/安全模块 | 架构师 | 2 |
| L4-重大 | 数据库变更/生产配置 | 架构师+项目总监 | 2 |

### 4.2 级别判定

| 变更类型 | 级别 |
|----------|:----:|
| 新增业务API | L1 |
| 修改公共模块(common-*) | L2 |
| 修改安全模块(common-security) | L3 |
| 修改数据库Schema | L3 |
| 修改生产环境配置 | L4 |
| 修改CI/CD配置 | L3 |

## 5. 审查意见规范

### 5.1 意见分类

| 标记 | 含义 | 处理要求 |
|:----:|------|----------|
| 🔴 Must Fix | 必须修改 | 修改后方可合入 |
| 🟡 Should Fix | 建议修改 | 尽量修改，可说明原因不修改 |
| 🟢 Nice to Have | 可选优化 | 自行决定 |
| 💡 Suggestion | 建议思考 | 讨论性质 |
| ❓ Question | 提问 | 需回复 |

### 5.2 意见格式

```
[标记] 问题描述
原因说明
建议方案（如有）
```

示例：
```
🔴 Must Fix: Controller中直接调用了Mapper
违反分层规范，Controller应调用Service而非直接操作数据层。
建议：将逻辑移至ModelService中。
```

## 6. 审查度量

### 6.1 审查效率指标

| 指标 | 目标 |
|------|:----:|
| MR首次响应时间 | < 4小时 |
| MR审查完成时间 | < 24小时 |
| MR平均审查轮次 | < 3轮 |
| MR合入率 | > 90% |

### 6.2 审查质量指标

| 指标 | 目标 |
|------|:----:|
| 审查发现的缺陷率 | > 2个/MR |
| 逃逸缺陷率(上线后发现) | < 10% |
| 审查覆盖率 | 100% |
