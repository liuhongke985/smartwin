## 2. 变更控制流程

### 2.1 变更流程

```
1.变更申请 → 2.影响分析 → 3.CCB评审 → 4.审批决策 → 5.实施变更 → 6.验证关闭
```

### 2.2 变更分类

| 变更类型 | 影响范围 | 审批人 | 时限 |
|----------|----------|--------|:----:|
| 小型变更 | <2人日，不影响里程碑 | 项目经理 | 1个工作日 |
| 中型变更 | 2-10人日，可能影响Sprint | 项目总监 | 3个工作日 |
| 大型变更 | >10人日，影响里程碑/预算 | 指导委员会 | 5个工作日 |
| 紧急变更 | 生产环境紧急修复 | 项目总监 | 即时 |

## 3. 配置管理

### 3.1 配置项

| 配置项类型 | 示例 | 版本控制 |
|------------|------|----------|
| 源代码 | Java/Python/Vue代码 | Git |
| 配置文件 | application.yml/Nacos配置 | Git+Nacos |
| 数据库脚本 | DDL/DML/迁移脚本 | Git |
| 部署脚本 | Dockerfile/docker-compose | Git |
| 文档 | 所有PMO文档 | Git |

### 3.2 分支策略

```
main (生产分支)
  ├── release/v1.0 (发布分支)
  │    ├── hotfix/xxx (热修复)
  │    └── ...
  └── develop (开发分支)
       ├── feature/IC-xxx (智链功能)
       ├── feature/SW-xxx (智赢功能)
       ├── feature/PF-xxx (共享底座)
       └── ...
```

| 分支 | 用途 | 合并规则 |
|------|------|----------|
| main | 生产代码 | 只从release合并，需总监审批 |
| release/x.x | 发布准备 | 从develop切出，只接收hotfix |
| develop | 集成开发 | 从feature合并，需CR通过 |
| feature/xxx | 功能开发 | 从develop切出，CR后合并 |
| hotfix/xxx | 紧急修复 | 从release切出，修复后合并回main和develop |
